# 合同审查智能体执行证据体检包

## 1. 适合谁

这个试点包适合已经有合同审查智能体、法务辅助智能体、合同问答工具或企业流程智能体的团队。尤其适合以下情况：

- 智能体会调用外部工具或企业系统。
- 输出结论可能影响审批、付款、合同谈判或风险判断。
- 已经有人工审核，但审核记录分散。
- 已经有日志，但日志不能直接回答“关键动作是否可复查”。
- 不希望在证据层保存合同全文。

不适合还没有稳定业务流程、还没有智能体原型、或希望一次性采购完整平台的团队。

## 2. 两周试点目标

两周试点只验证一个问题：合同审查智能体的关键动作，能否形成可签名、可校验、可复核的执行证据。

试点不追求覆盖全部合同场景，不建设 SaaS（Software as a Service，软件即服务）平台，不接入真实生产密钥，不承诺法律合规结论。

## 3. 客户需要提供什么

客户需要提供的是流程边界，而不是大量真实合同数据：

- 一个典型合同审查流程说明。
- 关键动作列表，例如检索条款、生成风险意见、触发人工复核、发送外部系统记录。
- 哪些动作出错后会有真实后果。
- 哪些动作需要人工审核。
- 哪些动作应该有外部系统回执。
- 可脱敏的样例输入、样例输出或字段结构。
- 当前日志或追踪记录的字段示例。

客户不需要在第一阶段提供合同全文、客户秘密、私钥、API key（Application Programming Interface key，应用程序接口密钥）或生产系统访问权限。

## 4. RedCrag 交付什么

试点交付物包括：

- 关键动作目录。
- AEP（Agent Execution Profile，智能体执行证据配置文件）证据包。
- demo（demonstration，演示）级签名与验签。
- validator（validator，校验器）规则。
- 一个正确样例。
- 至少四个错误样例。
- gap report（gap report，差距报告）。

这些交付物用于说明：哪些证据已经足够，哪些回执缺失，哪些人工审核缺失，哪些地方存在敏感信息泄露风险。

## 5. 试点验收标准

试点验收以可运行、可解释、可复查为准：

- 能生成一份 AEP（Agent Execution Profile，智能体执行证据配置文件）证据包。
- 能对证据包进行 demo（demonstration，演示）级签名。
- 能验证签名状态。
- 能运行 validator（validator，校验器）。
- 正确样例能够通过。
- 错误样例能够失败，并能解释失败原因。
- 能输出 gap report（gap report，差距报告）。
- 能说明哪些字段不会保存合同全文。

## 6. 不承诺什么

试点不承诺：

- 模型输出一定正确。
- 外部世界事实一定真实。
- 自动形成法律合规结论。
- 自动免除业务或法律责任。
- 已经具备生产级签名体系。
- 已经支持所有平台。
- 已经可以作为通用 SaaS（Software as a Service，软件即服务）产品上线。

## 7. 试点结束会沉淀什么

试点结束后，客户和 RedCrag 应该共同得到：

- 一份关键动作目录。
- 一份最小 AEP（Agent Execution Profile，智能体执行证据配置文件）字段映射。
- 一套 validator（validator，校验器）规则草案。
- 一组 specimen（specimen，样例集）。
- 一份 gap report（gap report，差距报告）。
- 一份下一步接入建议，例如 OpenTelemetry（开放遥测标准）映射、MCP（Model Context Protocol，模型上下文协议）工具插件或平台侧接头。
